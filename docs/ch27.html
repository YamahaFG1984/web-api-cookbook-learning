WebRTC 点对点通信

第 4 章的 WebSocket 让浏览器和服务器实时通信；第 18 章拿到了摄像头的画面。把两者结合起来，就是视频通话吗？ 可以，但所有音视频都要经过你的服务器中转，延迟高、带宽贵。WebRTC（Web Real-Time Communication）让两个浏览器直接连接， 音视频和数据点对点传输，延迟低到可以实时对话。视频会议、在线协作白板、P2P 文件传输、云游戏，都建立在它之上。

本章目标

  • 理解点对点连接为什么需要「信令」，以及 SDP offer / answer 的交换过程
  • 理解 ICE、STUN、TURN 如何穿越 NAT 和防火墙
  • 用 RTCPeerConnection 建立连接，用数据通道收发任意数据
  • 在连接中传输摄像头的音视频
  • 了解连接状态监控、网络拓扑（Mesh / SFU）和安全隐私问题

为什么需要点对点

WebRTC 由三组 API 组成：

🎥

getUserMedia

获取摄像头和麦克风（第 18 章已经学过）。

🔗

RTCPeerConnection

两个浏览器之间的连接：协商、穿越网络、加密、传输音视频，并根据网络状况自动调整码率。

📨

RTCDataChannel

在同一个连接上收发任意数据（文字、文件、游戏状态），可以选择可靠或低延迟模式。

27.1信令：交换 offer 与 answer

两个浏览器互相不知道对方在哪里、支持什么格式，怎么开始建立连接？

在直连之前，双方需要交换一些「自我介绍」：我支持哪些编解码器、我的加密指纹是什么、我可能在哪些网络地址上被找到。 这个交换过程叫信令（signaling）。WebRTC 规范故意没有规定信令怎么传 —— 你可以用 WebSocket、HTTP 轮询、 甚至把文字复制粘贴给对方。本章的跨标签页演示，就用第 2 章的 BroadcastChannel 当作信令通道。

SDP（Session Description Protocol）是一段文本格式的「会话描述」，大致包含：

v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
a=group:BUNDLE 0
m=application 9 UDP/DTLS/SCTP webrtc-datachannel     ← 一个数据通道
a=ice-ufrag:x1Qm                                     ← ICE 连接用的凭据
a=ice-pwd:p1b2w8nFJxK…
a=fingerprint:sha-256 7B:2E:91:…                     ← DTLS 证书指纹，用于加密握手时验明正身
a=setup:actpass

你几乎不需要手动阅读或修改 SDP，把它当作一个需要原样转交给对方的「信封」即可。

27.2穿越网络：ICE、STUN 与 TURN

两台电脑都在各自的路由器后面，用的是 192.168.x.x 这样的内网地址，它们怎么可能直接连上？

这就是 ICE（Interactive Connectivity Establishment）要解决的问题。浏览器会收集所有「可能联系到我」的地址，称为候选（candidate）， 交换给对方后，双方逐一尝试，找到能通的那一条：

⚠ 生产环境必须有 TURN

公司网络、对称型 NAT、某些移动网络下，直连会失败，这时只有 TURN 中转才能通。只配置 STUN 的应用，总会有一部分用户「怎么都连不上」。 TURN 服务器要转发全部音视频流量，带宽成本不低，通常用 coturn 自建，或使用云服务商的托管方案。

ⓘ 通话中途加轨道要「重新协商」

连接建立后再 addTrack（比如通话中才打开摄像头），会触发 negotiationneeded 事件，需要再交换一次 offer / answer。 双方同时发起协商时会发生「碰撞」，MDN 上的 Perfect Negotiation（完美协商）模式给出了标准解法： 约定一方为「礼让方」，碰撞时由它回滚自己的 offer。实际项目建议直接照搬这个模式。

27.6监控连接状态

通话中网络波动了，你想提示用户「连接不稳定」，断线时自动重连。

多人通话：Mesh 与 SFU

Mesh 结构下，每个人都要把自己的视频分别发给其他每个人，4–5 人以上时上行带宽和 CPU 很快就撑不住。 大多数视频会议产品使用 SFU（Selective Forwarding Unit）：每人只把视频发给服务器一次，由服务器按需转发给其他人。 开源方案有 LiveKit、mediasoup、Janus 等；它们都提供浏览器 SDK，底层依然是本章的 RTCPeerConnection。

安全与隐私

  • 强制加密：WebRTC 的所有媒体和数据都通过 DTLS / SRTP 加密，无法关闭。SDP 中的证书指纹保证了加密握手的对象就是信令里说的那个人 —— 所以信令通道本身也必须安全（HTTPS / WSS，并做身份认证）。
  • IP 地址暴露：点对点连接意味着对方能看到你的公网 IP。浏览器会用 mDNS 隐藏内网地址，但公网地址（srflx 候选）依然可见。对隐私敏感的场景，可以设置 iceTransportPolicy: 'relay'，只通过 TURN 中转。
  • 权限：摄像头、麦克风、屏幕共享都需要用户授权（第 18 章），浏览器会在标签页上显示录制指示。
✨ WebRTC 与其他实时技术
技术适合

RTCPeerConnection、数据通道、setLocalDescription() 无参调用、restartIce() 在各主流浏览器中都已 广泛可用。

小结

  • WebRTC 让浏览器之间直接传输音视频和数据，全程加密；建立连接前需要通过你自己选择的信令通道交换 offer / answer 和 ICE 候选。
  • setLocalDescription() 自动生成 offer 或 answer；icecandidate 事件产生的候选要转发给对方并 addIceCandidate()。
  • ICE 依次尝试本机地址、STUN 发现的公网地址、TURN 中转；生产环境必须部署 TURN。
  • createDataChannel / datachannel 事件收发数据；addTrack / track 事件传输音视频，replaceTrack 切换来源。
  • 用 connectionState 和 getStats() 监控连接；多人场景使用 SFU。
