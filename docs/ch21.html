Web Worker 与主线程

第 1 章说过：浏览器里的 JavaScript 只有一条主线程，它既要跑你的代码，又要响应点击、绘制页面。 网络请求可以交给浏览器在后台等待，可是如果是你自己的代码要算很久（处理大文件、压缩图片、解析巨大的 JSON）， 主线程就会被堵住，页面直接「卡死」。这一章讲怎么识别这种问题，以及两种解法：把活挪到 Worker 线程，或者把活切碎、给主线程喘息的机会。

本章目标

  • 理解事件循环：任务、微任务与渲染的顺序，以及「长任务」为什么会导致卡顿
  • 创建 Web Worker，用 postMessage 与它通信
  • 把 Worker 包装成返回 Promise 的函数
  • 用「可转移对象」零拷贝地传递大块二进制数据
  • 把长任务切片，用 scheduler.yield() 等方式让出主线程
  • 了解模块 Worker、OffscreenCanvas、SharedWorker 与 Comlink

事件循环：主线程在忙什么

主线程的工作方式像一个只有一个窗口的办事大厅：所有事情（你的脚本、事件回调、定时器回调、页面绘制）都要排队，一次只办一件。 这个「取一件事 → 办完 → 再取下一件」的过程叫事件循环（event loop）。

ⓘ 异步 ≠ 不阻塞

fetch 在等待网络时不占用主线程，因为等待是浏览器在后台完成的。但 Promise 和 async/await 本身不会把计算移到别的线程： await 之后的代码依然在主线程上执行。一段需要 2 秒的循环，写在 async 函数里也照样卡 2 秒。

21.4高效传递大块数据：可转移对象

要把一个 100 MB 的图片像素数组或音频数据交给 Worker 处理，复制一遍就要花不少时间和内存。

postMessage 默认使用结构化克隆（第 2、5 章提到过）：把数据完整复制一份给对方。 对于 ArrayBuffer、MessagePort、ImageBitmap、OffscreenCanvas 等可转移对象， 还可以选择转移所有权：内存直接「过户」给对方，瞬间完成，原来的变量随即失效。

试一试：复制与转移 64MB 数据的耗时对比（用 structuredClone 模拟 postMessage）
ⓘ 什么不能传？

结构化克隆不能处理函数、DOM 节点、类实例的方法（只会保留数据属性）和 Symbol。传递这些会抛出 DataCloneError。 所以 Worker 通信的「接口」应该设计成纯数据：对象、数组、字符串、数字、Date、Map、Blob、ArrayBuffer……

21.5不用 Worker：切片并让出主线程

有些工作必须在主线程完成（比如要操作 DOM 的批量更新），没法放进 Worker，但又不想让页面卡住。

办法是把一个大任务切成许多小段，每做完一段就主动「让出」主线程，让浏览器有机会渲染和响应用户输入：

让出方式特点支持
await scheduler.yield()让出后优先回到你的任务（排在其他普通任务前面），专为此场景设计Chromium 已支持，其他浏览器在推进
setTimeout(fn, 0)到处可用；但会排到队尾，嵌套多层后浏览器会强制至少延迟 4ms广泛可用
requestIdleCallback(fn)在浏览器空闲时执行，适合「不急」的工作（预加载、统计上报）Safari 尚未默认支持
requestAnimationFrame在下一次渲染前执行；适合与画面相关的分批更新（第 1 章）广泛可用
🔑 Worker 还是切片？
  • 纯计算、数据量大、耗时长（图像处理、压缩、加密、解析大文件、搜索索引）→ Worker。计算完全不占主线程，总耗时也更短。
  • 必须操作 DOM、或者任务本身不算太重、只是偶尔超过 50ms → 切片 + 让出。
  • 两者可以结合：Worker 负责算，主线程分批把结果渲染出来。

小结

  • 主线程一次只做一件事；超过 50ms 的长任务会阻塞渲染和输入。async/await 不会把计算移出主线程。
  • new Worker(url) 创建后台线程；双方用 postMessage / message 事件通信，Worker 中没有 DOM 和 localStorage。
  • 用「请求 id + Map」把 Worker 通信包装成 Promise，或者直接使用 Comlink。
  • 大块二进制数据用可转移对象零拷贝传递，转移后原变量失效。
  • 不能用 Worker 时，把任务切片，用 scheduler.yield()（降级为 setTimeout）定期让出主线程。
  • 模块 Worker 支持 import；OffscreenCanvas 让绘图也能离开主线程。
