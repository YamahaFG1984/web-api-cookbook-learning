第 15 章

性能测量

「页面有点慢」是一种感觉，「首字节 820ms，最慢的资源是一张 1.2MB 的图片」才是可以行动的事实。 浏览器内置了一整套 Performance API，可以精确记录页面加载、资源下载、你自己代码的耗时，并把这些数据交给你上报和分析。

本章目标

  • 理解性能条目（performance entry）与性能缓冲区，读懂高精度时间戳
  • 用 Navigation Timing 测量页面加载，用 Resource Timing 测量每个资源
  • 用 User Timing（mark / measure）给自己的代码计时
  • 用 PerformanceObserver 实时收集条目并批量上报
  • 了解 Core Web Vitals（LCP、INP、CLS）这些「用户体验指标」

性能条目与缓冲区

三个核心 API 分工明确，但它们产生的数据都放进同一个地方 —— 页面的性能缓冲区：

所有时间戳都是 DOMHighResTimeStamp：一个以毫秒为单位、可以带小数（部分浏览器精确到微秒级）的数字， 从页面开始加载那一刻（performance.timeOrigin）算起。随时可以用 performance.now() 获取「现在」的时间戳。

💡 为什么不用 Date.now()？

Date.now() 精度只到毫秒，而且会受系统时钟调整的影响（比如电脑自动校时，时间可能倒退）。 performance.now() 精度更高，并且单调递增，专门用于测量时间间隔。

收集到的指标可以在开发时用于调试，也可以在生产环境中采集真实用户的数据（这叫 RUM，Real User Monitoring）， 用第 4 章的 Fetch 或 Beacon 上报到你的分析服务。

15.1测量页面加载性能

你想知道页面加载过程中各个阶段花了多长时间。

这个对象有很多时间戳属性，它们按发生顺序排列，构成一条完整的加载时间线：

指标计算方式含义
首字节时间（TTFB）responseStart - startTime服务器多快开始回应（网络 + 服务器处理）
DOM 可交互domInteractive - startTimeHTML 解析完成
DOMContentLoadeddomContentLoadedEventEnd - startTime同步脚本和 defer 脚本都执行完
总加载时间loadEventEnd - startTime图片等所有子资源也加载完

navigation 条目的 startTime 永远是 0。除了时间，它还带有其他有用信息：transferSize（传输的字节数）、 type（'navigate' 正常打开 / 'reload' 刷新 / 'back_forward' 前进后退）、responseStatus（HTTP 状态码）、name（页面 URL）。

15.2测量资源加载性能

你想知道页面加载的每个资源（CSS、JS、图片、接口请求）分别用了多长时间。

每个资源一个条目。initiatorType 表示资源是由谁发起的：'link'（CSS）、'script'、'img'、'fetch'、'xmlhttprequest'、'beacon' 等。 用 Fetch API 发出的请求也会出现在这里，所以它同样可以用来监测真实用户访问你的接口有多快。页面加载后发出的请求，会在发出时陆续加入缓冲区。

⚠ 跨域资源的详细时间是 0

出于安全考虑，从其他源加载的资源（CDN 上的字体、第三方脚本）只公开 startTime、duration 等少数字段， DNS、连接、transferSize 等细节都是 0 —— 除非对方服务器返回了 Timing-Allow-Origin 响应头。 另外，缓冲区默认最多保存约 250 个资源条目，资源很多的页面可以用 performance.setResourceTimingBufferSize() 调大，或者改用 PerformanceObserver 边来边收。

现代补充：Core Web Vitals

上面的指标都是「技术视角」的。Google 提出的 Core Web Vitals 则从「用户感受」出发，只关注三件事： 主要内容多快出现、交互多快有反应、页面会不会乱跳。它们也是通过 PerformanceObserver 收集的。

✨ 支持情况与其他新条目类型

这些用户体验指标长期以来只能在 Chromium 中采集；近两年 Firefox 和 Safari 也陆续实现了 LCP 与 INP 所依赖的 API， CLS（layout-shift）目前仍主要在 Chromium 中可用。 此外，Chromium 还提供 long-animation-frame（LoAF）条目，能告诉你哪一段脚本导致了卡顿。 用 PerformanceObserver.supportedEntryTypes 可以查看当前浏览器支持哪些条目类型：

小结

  • 性能条目都在一个缓冲区里：用 getEntriesByType / getEntriesByName 查询，用 PerformanceObserver 监听（buffered: true 补齐历史）。
  • 时间戳是相对 timeOrigin 的高精度毫秒数；测时长用 performance.now() 而不是 Date.now()。
  • navigation 条目：TTFB = responseStart，DOM 可交互 = domInteractive，总加载 = loadEventEnd。
  • resource 条目：name 是 URL，responseEnd - startTime 是耗时；跨域资源需要 Timing-Allow-Origin 才有细节。
  • mark() 打点、measure() 计算区间，可附带 detail；同一个 mark 可复用于多个 measure。
  • 上报时注意：对象要先序列化、排除上报请求本身、批量发送、页面隐藏时补发；用户体验指标看 LCP、INP、CLS。

动手练习

  1. 写一个 timed(name, asyncFn) 高阶函数：执行前后自动打 mark，结束后创建 measure 并返回原函数的结果。
  2. 在你的项目里加一个「性能面板」：页面加载完成后在角落显示 TTFB、DOM 可交互时间和最慢的三个资源。
  3. 用 PerformanceObserver 统计页面上所有接口请求的平均耗时和最大耗时，每 30 秒用 console.table 打印一次。
  4. 用 Chrome 开发者工具的 Lighthouse 或「性能」面板测一次你的网站，对照 LCP、INP、CLS 的阈值找出一个可以改进的点。
