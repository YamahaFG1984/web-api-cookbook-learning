网络请求

几乎每个 Web 应用都要和服务器说话：拉取数据、提交表单、上传文件、接收实时推送。 这一章从「老前辈」XMLHttpRequest 讲到今天的标准 Fetch，再到三种特殊用途的通道：Beacon、Server-Sent Events 和 WebSocket。

本章目标

  • 知道 XMLHttpRequest 与 Fetch 的关系，会用 Fetch 发 GET / POST / 上传文件
  • 理解 Fetch 的两段式结构，以及「404 不会让 Promise 失败」这个新手最大的坑
  • 弄懂 CORS 跨域报错是怎么回事
  • 用 Beacon 可靠地发送统计数据
  • 分清轮询、SSE、WebSocket 三种实时通信方式，并知道各自适合什么场景

从 Ajax 到 Fetch

2000 年代中期，Gmail 和 Google Maps 让人们第一次见识到「不刷新页面也能加载新数据」的网页。 这种技术被称为 Ajax（Asynchronous JavaScript and XML），它背后的 API 就是 XMLHttpRequest（简称 XHR）。 名字里虽然有 XML，但它同样可以收发 JSON、表单和二进制数据。

本章涉及的通信方式一览：

API方向连接典型用途
XMLHttpRequest / Fetch请求 → 响应一次一个加载数据、提交表单、上传文件
Beacon浏览器 → 服务器（单向）发完就走，不看响应页面关闭前发送统计数据
Server-Sent Events服务器 → 浏览器（单向）长连接通知、行情、日志、AI 流式输出
WebSocket双向长连接聊天、协同编辑、在线游戏

4.1用 XMLHttpRequest 发请求

你要向接口发 GET 请求，而且需要兼容不支持 Fetch 的老浏览器。

XHR 是基于事件的 API，使用步骤固定为四步：

  1. 创建 new XMLHttpRequest()
  2. 监听 load 事件，在里面读取响应
  3. 调用 open(方法, URL)
  4. 调用 send() 真正发出请求

注意注释里的关键一句：HTTP 错误状态码（404、500）不会触发 error 事件。 对浏览器来说，服务器回了话就算「请求成功」，至于回的是什么内容，要你自己检查 event.target.status。

ⓘ XHR 还有用吗？

Fetch 已经被所有浏览器支持了很多年，新代码基本都用 Fetch。XHR 目前唯一的实用优势是 上传进度：xhr.upload.addEventListener('progress', …) 可以显示「已上传 45%」，而 Fetch 至今没有等价的简单写法。

4.2用 Fetch 发 GET 请求

你想在现代浏览器里用更简洁的方式发 GET 请求。

Fetch 是两段式的：fetch() 返回的 Promise 在响应头到达时就兑现了，得到一个 Response 对象； 响应体可能还在路上，需要再调用 response.json()（或 text()、blob()……）读取，它又返回一个 Promise。

Response 对象上常用的成员：

成员说明

ok状态码在 200–299 之间时为 true

body一个 ReadableStream，可以边下载边处理（见本章末尾）
💡 响应体只能读一次

响应体是一条「流」，读完就没了。先调了 response.text() 再调 response.json() 会报 TypeError: body used already。确实需要读两次的话，先 response.clone()。

⚠ 发 FormData 时不要手动设置 Content-Type

multipart/form-data 需要一个随机的 boundary（分隔符）参数，只有浏览器知道它是什么。 如果你手动写 'Content-Type': 'multipart/form-data'，缺了 boundary，服务器就解析不了。

插曲：CORS 跨域

学网络请求，几乎一定会遇到控制台里这行红字：「…has been blocked by CORS policy」。这不是你的代码写错了，而是浏览器的安全机制在起作用。

同源策略：默认情况下，https://a.com 上的脚本可以发出请求到 https://b.com， 但不能读取响应内容 —— 除非 b.com 的响应头里明确说「我允许 a.com 读」。这个「明确说」的机制就是 CORS（跨源资源共享）。

🔑 记住三点
  • CORS 是服务器端的配置。前端代码无法「绕过」CORS，只能让后端加响应头，或者通过同源的代理转发。
  • CORS 错误时 fetch 会拒绝（TypeError），但出于安全原因你拿不到具体原因，只能看控制台。
  • mode: 'no-cors' 不是解决办法：它让请求能发出去，但响应变成「不透明」的，你一个字节也读不到。

4.5发送 Beacon

你想发一个「发完就不管」的请求，比如用户离开页面时上报统计数据。

用户关闭标签页时，页面上正在进行的 fetch 很可能被浏览器直接掐断。 navigator.sendBeacon() 把请求交给浏览器在后台完成，即使页面已经卸载也会发出去。

  • sendBeacon 总是发 POST，返回一个布尔值表示「是否成功排入发送队列」，之后没有任何回调，也拿不到响应。
  • 数据量有上限（通常 64 KB），适合小体积的统计数据。可以先把用户操作攒在数组里，最后一次性发送。
  • 为什么用 visibilitychange 而不是 unload / beforeunload？因为在手机上用户往往是直接划掉应用，unload 根本不会触发；visibilitychange 是页面生命周期中最后一个可靠触发的事件。
✨ 也可以用 fetch(…, { keepalive: true })

给 fetch 加上 keepalive: true，效果和 beacon 类似（页面卸载后请求继续），但你可以自定义方法和请求头。 请求体同样有约 64 KB 的限制。Baseline 广泛可用 Chromium 还在推进一个更进一步的 fetchLater() API：预先登记一个请求，由浏览器在页面销毁时（或到达指定时间时）自动发出，目前仅 Chromium 支持。有限支持

4.6用 Server-Sent Events 接收服务器推送

你想接收服务器端的实时通知，又不想反复轮询。

先看看三种「实时」方案的差别：

SSE 基于普通的 HTTP：浏览器发一个 GET 请求，服务器不结束响应，而是保持连接，有事件时就往里写一段文本。 浏览器端的 API 叫 EventSource：

服务器返回的 Content-Type 必须是 text/event-stream，内容是一段段纯文本，每个事件以空行结束：

event: notice
data: Connection established at 10:51 PM, 2023-04-22
id: 3

event: heartbeat
data: ping

data: 没写 event 字段的消息，会触发通用的 message 事件
event:
事件类型，对应 addEventListener 的第一个参数；省略时为 message
data:
事件内容，前端从 event.data 读到（纯文本，JSON 需要自己 parse）
id:
事件编号。断线重连时浏览器会自动带上 Last-Event-ID 请求头，服务器可据此补发遗漏的事件
retry:
建议的重连间隔（毫秒）
⚠ HTTP/1.1 下的连接数限制

在 HTTP/1.1 下，浏览器对同一个域名最多同时维持 6 个连接，而且这是所有标签页共享的。 开 7 个带 SSE 的标签页，第 7 个就会卡住。使用 HTTP/2 或 HTTP/3（今天绝大多数 HTTPS 站点默认如此）就没有这个问题。

  • ws:// 与 wss:// 的关系，就像 http:// 与 https://。HTTPS 页面上只能连 wss://。
  • socket.readyState 表示连接状态：0 连接中、1 已打开、2 关闭中、3 已关闭。在 open 之前调用 send 会报错。
  • WebSocket 不会自动重连（这点和 EventSource 不同）。断线重连、心跳保活需要自己实现，或者使用现成的库。
✨ 下一代：WebSocketStream 与 WebTransport

WebSocket 有个缺陷：服务器发得太快时，消息会在内存里无限堆积（没有「背压」）。 WebSocketStream 用 Streams API 重新设计了它，目前仅 Chromium 支持 有限支持； WebTransport 基于 HTTP/3，支持多路流和不可靠数据报，适合游戏和音视频，已在 Chrome 与 Firefox 中可用，Safari 仍在推进中。 对大多数应用而言，WebSocket 依然是最稳妥的选择。

小结

  • XHR 是事件型的老 API，Fetch 是基于 Promise 的现代标准；只有需要上传进度时才考虑 XHR。
  • fetch 只在网络失败时拒绝，一定要检查 response.ok；响应体要再调 json() 等方法读取，且只能读一次。
  • body 的类型决定 Content-Type：JSON 字符串要手动设置头，FormData 千万别手动设置。
  • CORS 由服务器的响应头决定，前端无法绕过。
  • sendBeacon（或 keepalive）在 visibilitychange 时上报数据；注意数据必须先序列化。
  • 单向推送用 SSE（自动重连），双向实时用 WebSocket（需自己处理重连）。
