前端安全：XSS、Sanitizer、CSP 与 Trusted Types

回头看看这本书：第 3 章的路由用 innerHTML 渲染页面，第 12 章的组件用 innerHTML 写模板，很多示例都顺手把字符串拼进了 HTML。 只要其中有一点点内容来自用户，这就是一个跨站脚本攻击（XSS）漏洞。 这一章讲清楚 XSS 是怎么发生的，以及浏览器提供的几道防线：安全的 DOM API、HTML 清洗、内容安全策略（CSP）和 Trusted Types。

本章目标

  • 理解 XSS 的原理和危害，认识哪些 API 是危险的「接收器」
  • 用 textContent、DOM 方法安全地显示用户内容，正确校验链接地址
  • 必须渲染 HTML 时，用 Sanitizer API 或 DOMPurify 清洗
  • 用 CSP 限制页面能执行哪些脚本，作为第二道防线
  • 用 Trusted Types 从源头上锁住危险 API
  • 了解 SRI、iframe 沙箱、Cookie 属性、防点击劫持等其他防线

XSS：让你的网站替攻击者执行代码

浏览器无法区分「网站开发者写的脚本」和「被混进页面的脚本」—— 只要它出现在页面里，就以这个网站的身份运行， 能读取本站的 localStorage（第 2 章）、调用本站的接口、修改页面内容、记录键盘输入。这就是 XSS 的可怕之处。

🔑 根本原因只有一个

把「数据」当成了「代码」。用户输入的是一段文本，却被交给了一个会把字符串解析成 HTML 或 JavaScript 的 API。 所以防御的核心也只有一句话：数据就用处理数据的 API，永远不要让它经过「解析」这一步。

24.1认识危险的接收器

你想知道哪些 API 会把字符串当作代码来解析，写代码时要格外小心。

会把字符串「解析」成 HTML 或代码的地方，在安全领域叫做接收器（sink）。数据流入接收器之前，必须确认它是安全的：

危险的接收器风险安全的替代
el.innerHTML = str、outerHTML解析为 HTML，事件属性（onerror）会执行el.textContent = str
el.insertAdjacentHTML(pos, str)同上el.insertAdjacentText()、el.append(节点)
document.write(str)同上，还会阻塞解析DOM 方法
eval(str)、new Function(str)直接执行代码JSON.parse、查表
setTimeout('字符串', ms)字符串会被当作代码执行传函数：setTimeout(() => …, ms)
a.href = str、iframe.src = str、location = strjavascript: 开头的 URL 会执行代码先用 new URL 校验协议（见 24.2）
el.setAttribute('onclick', str)事件属性就是代码addEventListener
script.src = str、script.textContent = str加载或执行任意脚本只使用你自己控制的固定地址
⚠ 一个常见的误解：「script 标签不会执行，所以 innerHTML 是安全的」

通过 innerHTML 插入的 <script> 标签确实不会执行，但这根本拦不住攻击者： <img src=x onerror=攻击代码>、<svg onload=…>、<a href="javascript:…"> 等写法数不胜数。 不要试图用正则表达式「过滤掉危险标签」，HTML 的解析规则复杂到你几乎不可能写对。

24.3必须渲染 HTML 时：清洗

你的应用确实需要显示用户写的富文本（比如富文本编辑器的内容、Markdown 转换出的 HTML），不能全部当作纯文本。

这时要对 HTML 做清洗（sanitize）：解析 HTML，只保留允许的标签和属性（<b>、<a href>、<img src>……）， 删掉所有脚本、事件属性和危险的 URL。

浏览器内置的 Sanitizer API

✨ Sanitizer API 的现状

Sanitizer API 经过多年讨论后重新设计，Element.setHTML() 已开始在浏览器中正式发布，但截至 2026 年仍未在所有主流浏览器中可用。有限支持 使用前请检测 'setHTML' in Element.prototype，不支持时退回 DOMPurify。 （与之对应的 setHTMLUnsafe() 不做清洗，它存在的意义是支持第 12 章的声明式 Shadow DOM，千万别用它处理用户内容。）

成熟方案：DOMPurify

DOMPurify 由安全公司 Cure53 维护，是目前最广泛使用的 HTML 清洗库，也是很多框架文档推荐的方案：

⚠ 清洗之后就不要再改了

清洗必须是插入 DOM 之前的最后一步。清洗之后如果又做了字符串替换、拼接，或者在服务器清洗后前端再解码一次，都可能「复活」危险内容。 另外，服务器端也要对存储的内容做校验，不能只依赖前端。

24.4内容安全策略（CSP）：第二道防线

代码量大了，难免有某处疏忽用了 innerHTML。你希望即使出现漏洞，注入的脚本也执行不了。

CSP（Content Security Policy）由服务器通过响应头告诉浏览器：「这个页面只允许执行这些来源的脚本」。 不符合规则的脚本 —— 包括注入的内联脚本和 onerror 这样的事件属性 —— 都会被浏览器拒绝执行。Baseline 广泛可用

指令作用
script-src允许执行哪些脚本。推荐 'nonce-随机值' 'strict-dynamic'；避免 'unsafe-inline' 和 'unsafe-eval'
object-src 'none'禁用 <object> / <embed> 插件
base-uri 'none'防止注入 <base> 标签改变所有相对地址
default-src / img-src / connect-src …限制图片、fetch 请求等其他资源的来源
frame-ancestors 'none'禁止别的网站用 iframe 嵌入你的页面（防点击劫持，见 24.6）
report-to违规时向指定地址发送报告

先观察，再拦截

直接上线一个严格的 CSP，很可能误伤你自己的内联脚本或第三方统计代码。稳妥的做法是先用 Content-Security-Policy-Report-Only： 浏览器只报告违规、不真正拦截。收集一段时间报告、修正问题后，再切换为正式的 CSP。页面上也可以监听违规事件：

24.5Trusted Types：从源头锁住危险 API

项目很大、开发者很多，你希望「往 innerHTML 里塞一个普通字符串」这件事本身就直接报错，逼着所有人走安全的路径。

Trusted Types 是 CSP 的一个扩展。开启后，24.1 节表格里的那些危险接收器不再接受普通字符串， 只接受经过你定义的「策略」处理过的特殊对象（TrustedHTML、TrustedScriptURL……）：

它的价值在于把「安全」从「每个开发者每次都记得」变成了「不这样写就跑不起来」。 代码审查时，只需要检查少数几个策略函数，而不是全项目几百处 innerHTML。 Chromium 很早就支持 Trusted Types，其他浏览器近年也在陆续实现，使用前请查阅 caniuse。支持情况在变化 不支持的浏览器会忽略这条 CSP 指令，不会造成功能问题。

24.6其他防线

除了 XSS，前端还有哪些常见的安全问题，浏览器又提供了哪些开关？

子资源完整性（SRI）

从 CDN 加载第三方脚本时，如果 CDN 被入侵（第 19 章提到的 polyfill.io 事件），你的网站就会执行被篡改的代码。 integrity 属性写上文件内容的哈希（第 23 章），浏览器下载后会校验，不匹配就拒绝执行。本页的演示正是这样加载 DOMPurify 的：

iframe 沙箱

嵌入不可信的内容（用户上传的 HTML、第三方小部件）时，给 iframe 加上 sandbox 属性。它默认禁止脚本、表单、弹窗、顶层跳转，并把内容放进一个独立的「不透明源」； 需要什么能力再用 allow-scripts 等值逐项开放。本章的两个演示都运行在 sandbox="allow-scripts" 的 iframe 中，所以注入的脚本碰不到本页。

⚠ 不要同时开启 allow-scripts 和 allow-same-origin

对于同源的内容，两者同时开启时，iframe 里的脚本可以直接移除自己身上的 sandbox 属性，沙箱等于没有。

安全清单

  • 全局搜索 innerHTML、outerHTML、insertAdjacentHTML、document.write、eval，逐一确认数据来源。
  • 所有来自用户、URL、第三方接口、postMessage 的数据都视为不可信。
  • 外链只允许 http: / https: 协议。
  • 部署严格 CSP（先 Report-Only），能开 Trusted Types 就开。
  • 第三方脚本尽量自托管；从 CDN 加载时加 integrity。
  • 会话凭证使用 HttpOnly; Secure; SameSite 的 Cookie。
  • 前端的一切校验都能被绕过：服务器端必须再次校验和编码。

小结

  • XSS 的本质是数据被当作代码解析；注入的脚本拥有与你的网站相同的权限。
  • innerHTML 等「接收器」会解析字符串；显示用户内容用 textContent 和 DOM 方法，链接先用 URL 校验协议。
  • 必须渲染 HTML 时清洗：浏览器的 setHTML()（逐步普及中）或 DOMPurify。
  • CSP 用 nonce + 'strict-dynamic' 限制可执行的脚本，先 Report-Only 观察；Trusted Types 让危险接收器只接受经过策略的值。
  • SRI、iframe 沙箱、Cookie 属性、frame-ancestors、Permissions-Policy 构成其余的防线。
