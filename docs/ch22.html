Service Worker 与 PWA

到目前为止，我们做的所有网页都有一个共同的弱点：断网就打不开。原生 App 则不同，没有网络时至少能打开界面、显示缓存的内容。 Service Worker 让网页也拥有这种能力：它是一个运行在页面和网络之间的「代理」，可以拦截每一个请求，决定从缓存还是从网络取数据。 再加上一个描述应用信息的 Manifest 文件，网页就能像 App 一样被安装到桌面，这就是 PWA（Progressive Web App，渐进式 Web 应用）。

本章目标

  • 理解 Service Worker 的角色、作用域与生命周期
  • 用 Cache API 预缓存「应用外壳」（App Shell）
  • 在 fetch 事件中实现缓存优先、网络优先、stale-while-revalidate 等策略
  • 正确地发布新版本：清理旧缓存、提示用户更新
  • 编写 Web App Manifest，让网页可以被安装
  • 了解推送通知、后台同步等「App 化」能力，以及调试方法

ⓘ 浏览器什么时候检查更新？

每次导航到受控页面时（最多每 24 小时强制一次），浏览器会重新下载 sw.js 并逐字节比较。只要有一个字节不同，就视为新版本并开始安装。 所以发布新版本的常见做法，是修改文件里的版本号常量。检查 sw.js 更新时，浏览器默认会绕过 HTTP 缓存，但它 importScripts 引入的其他脚本仍受缓存影响。

22.3预缓存应用外壳

你希望网站在第一次访问后，即使断网也能打开基本界面。

应用外壳（App Shell）指的是显示界面所需的最少文件：HTML 骨架、CSS、核心 JS、图标。在 install 事件中把它们存入缓存：

  • event.waitUntil(promise) 延长事件的生命周期。如果 Promise 被拒绝（比如某个文件 404），整个安装失败，新版本被丢弃，旧版本继续工作 —— 这保证了缓存要么完整、要么不用。
  • Service Worker 随时可能被浏览器挂起以节省资源，所以不要在全局变量里保存状态，需要持久化的数据放进 Cache API 或 IndexedDB。

Cache API 速查

Cache API 专门存储「请求 → 响应」对，在 Service Worker 和普通页面中都能使用：Baseline 广泛可用

方法作用
caches.open(name)打开（不存在则创建）一个命名缓存
cache.addAll(urls)请求这些 URL 并全部存入（任一失败则全部失败）
cache.put(request, response)存入一个你已经拿到的响应（注意 Response 只能读一次，存之前要 clone()）
cache.match(request) / caches.match(request)在某个 / 所有缓存中查找，找不到返回 undefined
cache.keys() / caches.keys()列出缓存中的请求 / 所有缓存的名字
cache.delete(request) / caches.delete(name)删除一个条目 / 整个缓存
⚠ Cache API 不会自动过期

与浏览器的 HTTP 缓存不同，Cache Storage 中的内容永远不会自己过期或更新，完全由你的代码管理。 它和 IndexedDB 共享第 2 章提到的存储配额，写满了浏览器可能整体清除网站数据。所以要控制缓存的大小，并在新版本中清理旧缓存（22.5 节）。

22.4拦截请求：缓存策略

不同的资源有不同的需求：图标很少变化，要最快；新闻数据要尽量新；HTML 在线时要最新、离线时也要能打开。

所有请求都会触发 Service Worker 的 fetch 事件，调用 event.respondWith(响应或 Promise) 就能「代答」。常见的策略有：

策略速度新鲜度离线适用
缓存优先★★★★（需要版本号来更新）✓app.3f9a2c.js 这类带哈希的文件、字体
网络优先★（取决于网络）★★★✓（退回缓存）HTML、个人数据、订单状态
Stale-While-Revalidate★★★★★（晚一次）✓头像、不常变的接口、新闻列表
仅网络—★★★✗POST 请求、支付、统计上报
仅缓存★★★—✓install 时预缓存、永不变化的资源
⚠ 最容易踩的坑：把 HTML 永久缓存了

如果对 index.html 使用缓存优先，用户会永远看到第一次访问时的版本，发布多少次都没用，除非 Service Worker 本身更新。 HTML 请用网络优先；只有文件名带内容哈希、内容一变文件名就变的资源，才适合无限期的缓存优先。

22.6Web App Manifest 与安装

你希望用户能把网站「安装」到桌面或手机主屏幕，像 App 一样用独立窗口打开。

Manifest 是一个 JSON 文件，描述应用的名称、图标、主题色和打开方式：

name / short_name
完整名称，以及主屏幕图标下显示的短名称
start_url
从桌面图标打开时加载的地址
display
standalone：独立窗口，没有地址栏；fullscreen：全屏；browser：普通标签页
icons
各种尺寸的图标。实际项目中通常至少提供 192×192 和 512×512 的 PNG，以及用于 Android 自适应图标的 "purpose": "maskable" 版本
theme_color
标题栏、状态栏的颜色
浏览器安装方式
Chrome / Edge（桌面与 Android）地址栏的安装图标或菜单；页面可监听 beforeinstallprompt，用自己的按钮触发安装提示
Safari（iOS / iPadOS）分享菜单 →「添加到主屏幕」
Safari（macOS）文件菜单 →「添加到程序坞」
FirefoxAndroid 版支持添加到主屏幕；桌面版基本不支持安装

22.7推送通知与后台能力

你希望在用户没有打开网站时，也能给他发送通知（比如「你的订单已发货」）。

第 13 章的 Notification 只能在页面打开时由页面创建。推送则由服务器发起，经过浏览器厂商的推送服务，唤醒你的 Service Worker 显示通知：

能力作用支持
Push API服务器推送，唤醒 Service WorkerBaseline 2023 iOS 上仅限已添加到主屏幕的应用
Background Sync离线时提交的表单，等网络恢复后由 Service Worker 自动重发仅 Chromium
Navigation PreloadService Worker 启动的同时并行发出导航请求，减少延迟广泛可用
⚠ 推送通知要克制

推送权限的请求规则与第 13 章相同：必须由用户操作触发，而且大多数用户会拒绝「一打开网页就要求推送权限」的网站。 Chrome 等浏览器还会对通知骚扰严重的网站自动静默权限请求。只在用户明确需要时（如「订单发货时提醒我」）再请求。

调试 Service Worker

  • 开发者工具 → Application（应用）→ Service Workers：查看状态，手动 Update、Unregister，勾选 Update on reload（开发时每次刷新都安装新版本）。
  • Application → Cache Storage：查看、删除缓存条目。
  • Application → Storage → Clear site data：一键清空 Service Worker、缓存、IndexedDB 等所有数据，回到「首次访问」状态。
  • Network 面板：来自 Service Worker 的响应会标注「(ServiceWorker)」；勾选 Offline 模拟断网。
  • 地址栏输入 chrome://serviceworker-internals 可以查看浏览器中所有的 Service Worker。

小结

  • Service Worker 是位于页面与网络之间的可编程代理，只能在 HTTPS / localhost 下注册，控制范围由脚本所在目录（scope）决定。
  • 生命周期：install（预缓存）→ waiting（等待旧版本退场）→ activate（清理旧缓存）→ 处理 fetch；首次访问的页面不受控制。
  • Cache API 存储「请求 → 响应」，不会自动过期，需要自己管理版本和清理。
  • 按资源选择策略：HTML 网络优先，带哈希的静态资源缓存优先，其余 stale-while-revalidate；离线时返回后备页。
  • 发布新版本：修改 sw.js（版本号）→ 提示用户 → skipWaiting → controllerchange 后刷新。
  • Manifest + Service Worker + HTTPS = 可安装的 PWA；推送通知通过 Push API 在页面关闭时也能送达。
