第 19 章

结语：与不断变化的 Web 平台相处

走到这里，你已经见识了浏览器内置的几十个 API：从 Promise 到 IndexedDB，从观察者到 Web Components，从剪贴板到摄像头。 最后一章不讲新的 API，而是讲几条「元知识」：什么时候还是该用库、如何判断一个 API 能不能用、如何为旧浏览器兜底，以及未来还有什么值得期待。

本章目标

  • 在「原生 API」与「第三方库」之间做出合理的取舍
  • 掌握特性检测，避免浏览器版本嗅探
  • 理解 polyfill 的作用与局限（以及它的安全风险）
  • 了解 Web 标准从提案到 Baseline 的过程，以及正在到来的新 API
  • 用一张表回顾全书涉及的 API 在 2026 年的支持情况

19.1为第三方库说句公道话

本书反复强调「不用库也能做到」，但这不意味着要不惜一切代价避免依赖。原生 API 往往只提供最底层的能力， 你可能需要写不少「胶水代码」才能把它变成顺手的工具。IndexedDB 就是典型：功能强大，但回调式的 API 用起来很痛苦（第 5 章）， 所以才有 idb、Dexie.js 这样的封装库。

💡 一个实用的判断顺序
  1. HTML / CSS 能直接做到吗？（loading="lazy"、<details>、popover、容器查询、@starting-style……）
  2. 原生 JS API 加少量封装能做到吗？（本书的大部分配方）
  3. 有没有「薄」的库，只是把原生 API 包得更好用？（idb、web-vitals）
  4. 最后才考虑「厚」的、自带一整套实现的库。

19.2检测特性，而不是浏览器版本

想判断用户的浏览器是否支持某个 API，你可能会想去解析 navigator.userAgent，看看是哪个浏览器的哪个版本。请不要这样做： UA 字符串极不可靠（各家浏览器都在里面互相「冒充」），用户也可以随意伪装；更重要的是，浏览器会不断更新，你写死的版本表很快就会过时。 正确的做法是直接检测你需要的那个特性是否存在：

⚠ 「存在」不等于「能用」

有些 API 在浏览器里存在，但因为缺少硬件（振动）、缺少权限（定位）、不在安全上下文（剪贴板）或被用户禁用（localStorage）而无法使用。 所以除了特性检测，调用时仍然要处理 Promise 的拒绝或 try/catch 抛出的异常 —— 这也是本书每一章都在强调错误处理的原因。

19.3Polyfill

需要支持旧浏览器时，可以借助 polyfill：一段用 JavaScript 实现缺失功能的第三方代码，让旧浏览器「假装」原生支持新 API。 它通常不如原生实现快，但能让你今天就用上新 API 的写法。

⚠ polyfill 也是供应链风险

2024 年，曾被数十万网站引用的 polyfill.io 域名易主后，被用来向访问者注入恶意代码 —— 这是近年影响最广的前端供应链事件之一。 教训：从第三方域名直接加载脚本，等于把你网站的控制权交给了对方。polyfill 应该通过包管理器安装、随项目一起构建和部署（自托管），并且只在需要时加载。

ⓘ 构建工具可以帮你

如果项目使用 Babel、Vite 等构建工具，可以用 browserslist 声明要支持的浏览器范围（例如 baseline widely available）， 工具会据此自动转换语法、按需注入 core-js 等 polyfill，你不必手动判断每一个 API。

2026 年值得关注的方向

🤖

浏览器内置 AI

Chrome 已发布翻译（Translator）、语言检测、摘要（Summarizer）等基于本地模型的 API，更多提案仍在推进中。有限支持

🎮

WebGPU

新一代 GPU 接口，用于 3D 渲染和通用计算（包括在浏览器里运行机器学习模型）。三大引擎均已在部分平台发布。

🚀

更少 JS 的交互

Popover、Invoker Commands、锚点定位、滚动驱动动画、跨文档视图过渡：越来越多的交互可以只用 HTML 和 CSS 完成。

📱

更像 App 的 Web

PWA 安装、推送通知、文件处理、后台同步……Web 应用与原生应用的界限持续模糊。

去哪里追踪最新进展

  • MDN Web API 索引：所有 API 的文档与兼容性表，实验性 API 会有明确标记。
  • Can I use：按功能查询各浏览器、各版本的支持情况，现在也显示 Baseline 状态。
  • webstatus.dev：官方的 Baseline 数据看板，可以查看每个特性何时成为 Baseline。
  • web.dev 博客 与各浏览器的发布说明（Chrome、Firefox、Safari Technology Preview）。
  • W3C 标准与草案、WHATWG 规范、TC39 提案：最权威但也最枯燥的来源，遇到边界情况时查阅。

写在最后

浏览器早已不是「显示文档的软件」，而是一个功能完备的应用平台。本书的每一个配方都在说明同一件事： 在引入依赖之前，先看看浏览器自己能做什么。同时也请记住本书反复出现的几条原则：

  • 先检测，再使用：特性检测 + 降级方案，而不是假设所有人都用最新的 Chrome。
  • 永远处理错误：Promise 可能被拒绝，权限可能被拒绝，网络可能断开。
  • 尊重用户：隐私（定位、摄像头、剪贴板）要先征得同意，动画要尊重 prefers-reduced-motion，交互要考虑键盘和屏幕阅读器用户。
  • 保持好奇：Web 平台每个月都在变化。你今天用 20 行 JS 实现的功能，明年可能一个 HTML 属性就能搞定。

毕业练习

  1. 挑一个你熟悉的项目，列出它依赖的第三方库，逐一判断：哪些可以用本书的原生 API 替代？替代后能减少多少体积？
  2. 综合运用本书知识，做一个离线可用的「笔记应用」：IndexedDB 存储（第 5 章）、表单校验（第 7 章）、Web Components（第 12 章）、导出文件（第 10 章）、国际化日期（第 11 章）、对话框确认删除（第 13 章），并为每个非 Baseline 特性写好降级方案。
  3. 去 webstatus.dev 找一个最近刚成为 Baseline 的特性，写一个小演示页面分享给同事。
